# Atlas · 教学方法论（全站）

> 层级：**全局方法论**。回答"一模块怎么写"和"一本手册怎么组织"，跨课题通用。
> 视觉/工程见 [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md)；课题专属参数见各课题 `TOPIC.md`；操作清单见 `/spec-patch.md`。

## 1. 三条设计原则

1. **痛点先行**——Part 1 永远是"朴素做法为什么会骗人"。认知冲突先于方法论。
2. **具体胜过编造**——优先使用真实事件、公开披露和实际口径解释概念；没有必要的可比数据时直接说明未知，不为凑例子编人物、金额或计算题。
3. **事实与判断分层**——交代事件、当事人主张、估算、条件预测及缺失证据；没有资料支撑时不用图表。

## 2. 模块教学骨架

常用节奏是：痛点 → 概念与事件/计算 → 对应证据和适用条件 → 速查 → 自测 → 小结、下一章。高密度素材优先按人物和事件推进；模型课题保留必要的手算数据与口径说明。事实与判断边界直接放在相关段落，不另设重复板块；“三个坑”不是必备模块，也不靠凑满卡片数表现教学完整性。

速查卡和自测用于巩固正文，不承载正文没有讲过的重要信息。图表只在可核验数据或清晰的计算输入支持时使用；没有可靠序列就不配图，不为通过校验构造图或数字。

## 3. 写作规范

- **语言**：口语化、第二人称、短句；允许比喻和情绪（"但这张图撒了谎"——这类句式的合法位置是一句号后立刻给精确表述）。
- **checklist**：动词开头、可检验（"能解释……"而不是"理解……"）。
- **类比**：只负责"直觉"，紧随其后就回到精确表述。每个课题有自己的类比池（放在该课题 `TOPIC.md`）。
- **口诀**：小结必须带 `mnemonic-line`。概念卡必须带 `c-mnemonic` 或记忆点——记忆锚点是内容的一部分。
- **段首先给读者地图**：解释性正文的每段先用一句明确的总结句点出人物、事件、结论或口径，再接事实、数字和判断边界。高密度故事的段首可写成 `<strong class="para-lead">一句总结。</strong>`，单独占一行；不要把同一个结论在后文换词重说，也不要把事件改写成脱离人物的空泛方法论。
- **每段只划少量重点**：段首导读之外，用 `<strong>` 高亮最关键的事实、数字、转折或限定条件；通常再挑 1 处即可，必要时 2 处，不要整段加粗。数字与核验边界须一起保留，不能因为强调而把估算写成定论。
- **按内容拆段**：一段只承担一个主要意思；遇到不同人物、交易、时间节点或财务口径就自然换段，并给新段自己的总结句。长段原则上控制在约 80～160 个汉字，超过约 180 字先检查能否按事件拆开；不为凑字数删掉原有事实，也不为凑格式写无信息的空话。手机窄屏上检查是否能快速扫到每段重点。

**内容节奏**（隐性，最易写崩的四条）：

1. **问题式标题**：页面 h1 和小标题尽量指出真实人物、事件或判断；无图页面不强行编图号。
2. **窄屏优先**：复杂信息用可纵向阅读的事实卡；确需阈值表时说明计算口径，并验证 320px 手机宽度不横向溢出。
3. **反直觉**：每隔 2~3 个 Part 必须有一个"你以为 X，其实 Y"的强调，落在具体数字上。写完感觉通篇没打脸点 → 数据故事太平，要么不该写这个模块，要么知识密度不够。
4. **口语计数**：数字必须跟时间/量级/对比对象绑定（"上线时 vs 9 个月后""128 倍""0.02 → 0.179"）。

**自测题**：难度递进 = 事件复盘 → 概念辨析 → 关键数字/证据的口径 → 争议判断 → 迁移排查；只有可核验数据或清楚标明输入与公式的必要教学计算时才设置计算题。答案藏在 `details` 里，关键结论在前加粗，做到能反推回对应 Part。

### 有高密度素材时的叙事约束

**零前置阅读**：假设读者没看过提供的资料。各章的连续正文应讲清起因、时间线、人物、事件、相反解释与结论；资料里独有的细节不能只散落在目录、脚注或自测里。

1. 先把事件按顺序放进各章，各章开头接上上一章的结果。概念、事实卡和论证边界只有带来正文未呈现的新信息时才另设板块；同一组人物、数字和限定条件在连续叙事中已讲清，就不要再复述一遍。
2. 已给出具体人物、交易和数字时直接讲这些事实与估算，不要改写成泛化方法论，也不要插入虚构公司、演练账户、假设金额或演练图。
3. 不反复对读者说“原文”“笔记称”“作者说”。来源和核验入口集中放在 `data/SOURCES.md`；正文自然叙述，并在事实不确定时写清时间、估算、争议方和证据缺口，不把转述升级成已核实结论。
4. 手机上的并排多列表格改为纵向事件卡；桌面可按两列布局，但阅读顺序与信息必须相同。
5. 每章至少有一道题返回具体人物、时间或事件，题目不得依赖未发生的演练场景。

## 4. 课题原型（4 种）——开新课题第一件事是选型

| 原型 | 适用 | 核心 Part | 自测侧重 | 图表侧重 |
|---|---|---|---|---|
| 计算/模型型 | 信贷、量化、定价、归因 | 手算一遍（method-step + calc-box） | 计算题 | 曲线、分布、散点 |
| 制度/法规型 | 合规、监管框架、合同条款 | 条文拆解 + 真实行为的适用边界（概念卡 + callout） | 规则判断题 | 流程图、对照表 |
| 流程/实务型 | 发行全流程、尽调、运维 | 真实流程 + 文档样例（case-step + method-step） | 排序、找错题 | 时间轴、泳道图 |
| 概念/框架型 | 宏观、行业研究、比较法 | 框架对比 + 事件复盘（concept-grid 为主） | 辨析、迁移题 | 矩阵、因果图 |

**数量规则（按教学需要，不为凑数）：**

| 项 | 通常范围 | 校验器约束 |
|---|---|---|
| 独立坑板块 | 默认省略；必要提醒融入对应正文 | 不强制；出现冗余板块时提示复查 |
| 自测 | 4~7 | 目前恰好 5 |
| 速查卡 | 6~10 | 目前 8~9 |
| 模块数 | 4~10 | — |

## 5. 跨模块叙事线

至少找到一条能贯穿课题的真实时间线、人物关系、制度变化或可核对的数据口径。连续故事是主线，不需要为串联模块构造共同虚构账户。

- 需要跨章复算同一份数据时，可将数据放进 `data/` 并登记 `narrative.json`：真实数据注明出处与日期；必要的教学构造数据必须明确标注“非真实业务数据”，只用于演示计算，不写成真实客户或真实上线故事。
- 以人物与事件推进的 source-driven 课题，不强制 `case.csv`、`narrative.json`、Chart.js 图或手算段落。
- 每个新模块写完，按 `/spec-patch.md` 核对目录、正文、样式和引用。

## 6. 学习效果层（会越用越差的方向）

- 自测：建议"先写后看"——`<summary>` 提示把答案写在纸上再展开；答案末尾加"↩ 回看 Part N"锚点。
- 读起来 ≠ 记住：`review.html`（跨模块综合题 / 口诀汇总 / Anki 导出）作为复习层。
- 工作映射：`reports/` 作为课题输出区——学习日志、与工作边界的映射。
- 延伸阅读：参考教材章节 / 监管文件 / 实务来源（防止单点深度锚点）。
